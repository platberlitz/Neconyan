# Server ownership audit

The application is not fully server-owned. Provider requests reaching a server endpoint do not make the surrounding browser workflow independent of an open page.

### Historical Stage 9 checkpoint

Stage 9 is verified locally, on top of verified Stage 8. A migrated Roleplay control now names one server workflow and hands over only what the user typed or what a saved extension had already written down. The server owns the named vocabulary, the effect, the anchor, the prompt contributions, the connection, the capacity reservation, the permanent receipt and the single journalled protected write. The browser observes the accepted job, reloads the chat the server wrote and adopts the saved result facts, so a reopened page reattaches to accepted work instead of submitting it again.

The named vocabulary is `roleplay.reply`, `roleplay.continue`, `roleplay.swipe`, `roleplay.correct`, `story.passage`, `guided.response`, `guided.swipe`, `guided.correction`, `deep-swipe.reply` and `deep-swipe.user`. Each name maps to one effect, one anchor rule and one prompt slot. The four plain controls keep the saved automatic swipe and continuation policy, frozen at admission as in Stage 8; Story, Guided and Deep Swipe never capture it, so each is exactly one bounded model turn. Page-only prompt additions such as Dialogue Colours, summaries and `/inject` values are resolved in the page into bounded, macro-free entries that the server validates, hashes into the named record and publishes on every turn under a `page_` prefix. An addition that cannot travel exactly, such as an Agent, Pathfinder or vector prompt, a scan-enabled inject, enabled vector retrieval or an unknown generation interceptor, keeps that generation on the browser path, as does the built-in helper assistant. Deep Swipe gained a new `alternative` effect that appends one more unselected swipe to the anchored message and leaves its selected text, index and metadata untouched. Private asides became native events: the browser states only the fact and the server keeps Roleplay reactions opt-in, samples, chooses the recipient from the saved group members or the solo thread who opted in, and reuses the existing cooldown, activity, busy and receipt rules. The browser takes one decision in one place, so the host's destructive browser steps and the native workflow cannot disagree, and a migrated regenerate or swipe no longer deletes the text the server is about to replace. The World Info settings binding (`roleplaySettingsHash`) ignores only page bookkeeping, namely save counters, mirrored browser storage and the Conversation store, so a routine page save cannot fail an accepted reply while every setting a prompt reads still stops the turn before paying.

### Historical Stage 8 checkpoint

Stage 8 is verified locally, on top of verified Stage 7 at `fa5050578`. One saved progressive workflow carries a whole accepted Roleplay turn. It admits itself once with a permanent media receipt, then progresses through indexed `roleplay.candidate` children attached to the parent in a single ledger write before release. A candidate saves its result without writing chat, so the previous reply, its selected swipe and unrelated history survive until one journalled protected write publishes the final text.

The account lock and job runner own the whole progression. The parent parks in a waiting state while a child, an owner approval or a paid model turn is outstanding, and the waiting resolver requeues it only when its own children are complete. A model tool call becomes a real child job attached to the root, and the root resumes the model with a complete server-proven assistant function-call and tool-result pair. A child that mutates a book, Agent, preset, character or the chat must prove its own permanent physical effect before the parent may recapture the protected source and bound World Info; several mutating calls in one model reply progress in order, each with its own proof. Automatic swipe and continuation decisions are saved before the next paid turn, a rejected reply is kept as an earlier swipe in the final write, and continuations assemble into one final message. Group speakers are frozen at admission and published one at a time, each starting from a source proved to be the previous speaker's own write. The final write is journalled as writing before it happens, and the receipt closes only after the current chat is proved equal to that last owned write.

## Fixed in this audit

- Mewmory automatic extraction and full backfill now run as server jobs. Intent and progress are saved in the existing per-user story archive. Closing the page or changing chats does not cancel them. Startup scans resume interrupted work; explicit cancellation remains available.
- Internal model requests preserve their parent request's resumable behaviour and cancellation signal. Saved Mewmory connection profiles use that shared path rather than maintaining a second cancellation implementation.
- The Conversation send API saves the user's message before contacting the model. Failed requests retain that message. A completed reply merges into the latest store when its original branch is unchanged, preserving unrelated settings and other threads. Concurrent changes to the same branch still produce a conflict instead of overwriting messages. Failed regeneration keeps the previous reply.
- Manual Mewmory recall and complete index rebuilds now use saved jobs and private provider-result files. The real index control has been tested through acceptance, page unload and saved completion before reopening.
- A separate accepted Conversation reply API captures saved context and named chat or text-completion profiles, then saves reply bubbles and command effects with native completion records. Participant bindings are saved before acceptance and reused after batching. The main composer, the forced-reply action and the branch-from-message action now submit through it; the browser appends no messages of its own and only observes saved results.
